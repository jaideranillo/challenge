# TASK-002-03: V2 migration — `deliveries`, its indexes, and the partial unique index

## Feature

FEAT-002 — Webhook notification delivery, persistence schema

## Assigned Agent

`dba` — this task is only for this agent. If it needs work from another role, that's a separate task, not scope creep on this one.

## Supersedes its own earlier scope — read this first

This file previously specified a **range-partitioned** `deliveries` table (monthly on `created_at`). That scope was implemented and then **reversed by the user**: partitioning is deferred entirely (ADR-003 §3, rewritten), because the Postgres rule that a partitioned table's unique index must include the partition key forced the ADR-003 §2 idempotency invariant off `deliveries` and onto a side table (`deliveries_live_index`) maintained by a trigger (`trg_deliveries_live_index`) — complexity the user judged unjustified at this data volume.

The old scope, including that side table and trigger, is superseded. The work to do now is the **simple, textbook shape**: one plain table, a single-column primary key, real foreign keys, and a native partial unique index. This is a re-implementation, not an incremental edit, so:

- **Rewrite `V2__deliveries.sql` in place.** The migration has not been committed and is not applied in any durable environment — it is working-tree-only (`src/main/resources/db/` is untracked). Replace its contents; do **not** stack a corrective V5 on top.
- **`deliveries_live_index` and `deliveries_live_index_maintain()` / `trg_deliveries_live_index` must not exist anywhere in the final V2.** They are not "kept for safety" — they are the workaround being removed, and keeping them would reintroduce two writers of the same invariant.

### No partitioning

`deliveries` is a **plain, unpartitioned table**. No `PARTITION BY`, no child partitions, no `DEFAULT` partition. ADR-003 §3 now records partitioning as a deferred future performance improvement; implementing it is out of scope for this task and for this feature. If you believe volume justifies revisiting it, that is a conversation with the architect leading to a superseding ADR — not a migration.

### The idempotency invariant — implemented natively, no mechanism decision to make

ADR-003 §2's invariant is *at most one non-terminal `deliveries` row per `(event_id, subscription_id)` at any time, enforced by the database*. With no partitioning, PostgreSQL expresses that directly:

```
CREATE UNIQUE INDEX <name> ON deliveries (event_id, subscription_id)
  WHERE status NOT IN ('DELIVERED', 'DEAD', 'FAILED');
```

That single index **is** the mechanism. There is no decision left to weigh here and no trade-off to record — the previous version of this task asked the DBA to choose between three mechanisms only because partitioning made the native one impossible.

Consequences that follow for free and should be stated plainly in the completion note rather than left implicit:

- The invariant is enforced under concurrency by standard Postgres unique-index insertion locking: two concurrent inserts of a live row for the same pair produce exactly one success and one `23505`, with no deadlock and no application-level check-then-write (which would fail open — OWASP A10, the exact failure ADR-003's own security table warns about).
- Once the first row reaches a terminal status it leaves the index's predicate, freeing the pair — which is what makes `POST /replay` (ADR-005 §1) and internal recovery (ADR-003 §1.1) insert-not-mutate.
- `delivery_id` is database-guaranteed unique again, so the API's public identifier rests on a constraint rather than on a UUID-collision assumption.

### Indexes required (ADR-003 §3 list, with `idx_deliveries_due` from ADR-002 §2.1)

| Index | Definition / source |
|---|---|
| `idx_deliveries_due` | **ADR-002 §2.1, which explicitly supersedes ADR-003 §3's narrower version.** `CREATE INDEX idx_deliveries_due ON deliveries (next_attempt_at) WHERE status IN ('PENDING', 'RETRYING', 'QUEUED', 'PROCESSING');` — partial, so terminal rows leave the index automatically. Use **this** definition. Do not use a `(status, next_attempt_at)` composite from ADR-003's "Consequences" section; ADR-003 §3 itself defers to ADR-002 §2.1. |
| partial unique on `(event_id, subscription_id)` | `WHERE status NOT IN ('DELIVERED', 'DEAD', 'FAILED')` — ADR-003 §2 and §3, directly on `deliveries` as above. |
| `(subscription_id, status)` | The per-subscription in-flight count for the bulkhead / `max_concurrency` check (ADR-003 §3, ADR-006 §1.3, ADR-006 §2). The counted statuses are `QUEUED` and `PROCESSING`. Whether to make this index partial on those two statuses is your call; ADR-003 §3 asks only for `(subscription_id, status)`. If you make it partial, justify it, and be aware a partial index here is only usable by a query whose predicate matches. |
| `replayed_from` | Chaining a replay's or recovery's history back to its original (ADR-003 §3). Keep it even though the FK now exists — a FK does not create an index on the referencing side. |
| `(client_id, created_at)` | The list endpoint's default ordering and date-range filter, keyset-paginated (ADR-003 §3, ADR-005 §1). |
| `(client_id, status)` | The `delivery_status` filter (ADR-003 §3). The filter value arriving from the API is the **public** vocabulary and is expanded to internal states by the application before it reaches SQL; the index is on the internal `status` column. |

Six indexes total, all plain (non-partitioned) indexes on one table. There is no per-partition propagation to verify any more.

### Foreign keys — all three are creatable, none may be dropped

With a single-column `PRIMARY KEY (delivery_id)` and no partitioning, every FK ADR-003 §3 implies works normally. All of these are **required**, and the previous scope's decision to drop the first one is reversed:

- `replayed_from -> deliveries(delivery_id)` — self-referential, nullable. **Restored.** It was dropped only because the composite PK left `delivery_id` without its own unique constraint.
- `event_id -> notification_events(event_id)` — unchanged, worked before.
- `subscription_id -> subscriptions(subscription_id)` — unchanged, worked before.

The FK **into** `deliveries` from `delivery_attempts.delivery_id` is TASK-002-04's concern, but the single-column PK here is what makes it creatable there — say so in the completion note, since TASK-002-04 reads this note as a hard input.

Choose and state `ON DELETE` behavior for `replayed_from` explicitly (nothing in the ADRs deletes a `deliveries` row, so `NO ACTION`/default is defensible — but say which and why rather than leaving it to the reader).
